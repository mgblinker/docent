# Cryptography Policy (ISO/IEC 27001:2022 Annex A.8.24)

> DRAFT. Status column reflects the state at time of writing; verify each row
> before presenting to an auditor. Nothing marked "Planned" is implemented yet.

## 1. Purpose and scope

Defines when and how cryptography protects Processity information assets:
data at rest, data in transit, backups, and secrets. Applies to all production
and UAT infrastructure, all services in the Processity platform, and their
backups. Local developer environments are out of scope but must not contain
production data.

## 2. Principles

- Cryptographic controls are chosen from the risk assessment, not applied
  blindly. Each control below references the risk it treats.
- Only current, publicly reviewed algorithms are used (see section 5). No
  proprietary or home-grown cryptography.
- Keys are managed separately from the data they protect.
- Every control has evidence an auditor can inspect (section 7).

## 3. Controls

| # | Asset | Control | Threat treated | Status |
|---|---|---|---|---|
| C1 | PostgreSQL data (all service DBs) on prod-server | Full-volume encryption (LUKS2, AES-XTS-256) on the volume holding the Docker data directory | Theft or loss of disk, provider snapshot, decommissioned hardware | Planned |
| C2 | Database backups and WAL archives | Encrypted before leaving the host (`age`, asymmetric; private key held offline) | Backup theft, offsite storage compromise | Runbook ready (`docs/cicd/postgres-backups.md`), awaiting one-time setup + deploy |
| C3 | Object storage (FileService, Avatars: SeaweedFS / Infomaniak S3) | Server-side encryption at rest on the storage backend | Storage-level compromise | Planned |
| C4 | Postgres connections (service to DB) | TLS, `SSL Mode=VerifyFull` (Npgsql) with a private CA | Network interception between containers or hosts | Planned |
| C5 | Client to platform traffic | TLS at the Caddy entrypoint, HSTS | Interception on the public network | In place (verify config) |
| C6 | Highly sensitive columns (tokens, API keys, selected PII) | Application-level AES-256-GCM, key held in KeyVault | Insider or DB-admin access, SQL dumps | Assess per column |
| C7 | Secrets (DB passwords, SMTP, API keys) | Stored in KeyVault, injected at deploy time, never committed | Secret leakage via repository | Partly in place (see findings) |
| C8 | Passwords | Salted, adaptive hash (not reversible encryption) | Credential database compromise | Verify in Authentication service |

## 4. Key management

| Aspect | Rule |
|---|---|
| Generation | On a trusted host with a CSPRNG; LUKS keys generated by `cryptsetup` |
| Storage | LUKS passphrase or keyfile: sealed copy in the password manager of two named custodians. Backup encryption private key: offline, separate from the backup location. App-level keys: KeyVault |
| Access | Named custodians only; access reviewed at least annually |
| Unlock at boot | Documented procedure (manual unlock or Clevis/Tang). Reboot runbook covers it |
| Rotation | LUKS: re-key on custodian change or suspected compromise. App-level keys: at least annually, with key-id in the ciphertext so old data stays readable |
| Recovery | Loss of all LUKS key material means permanent data loss. Recovery test performed at least once a year |
| Revocation and destruction | Removed keys are destroyed and the removal logged |
| Compromise | Treated as a security incident under the incident process; affected data re-encrypted with a new key |

## 5. Approved algorithms

- Symmetric: AES-256 (XTS for disk, GCM for application data)
- Asymmetric: RSA 3072+ or Ed25519 / X25519 (`age`)
- Hashing: SHA-256 or stronger; password hashing via Argon2id, bcrypt or PBKDF2 with a current work factor
- TLS: 1.2 minimum, 1.3 preferred

## 6. Roles

| Role | Responsibility |
|---|---|
| Policy owner | Maintains this policy; reviews at least annually |
| Key custodians (two named) | Hold key material, perform unlock and recovery |
| Engineering | Implements controls, keeps status column current |

## 7. Evidence to retain

- C1: `cryptsetup status <volume>` and `lsblk -f` output, dated
- C2: backup job config plus a dated restore-test record
- C3: storage backend encryption setting (screenshot or config export)
- C4: connection strings showing `SSL Mode=VerifyFull`, `SHOW ssl;` on each DB
- C5: TLS scan result (e.g. SSL Labs report)
- C6 / C7: KeyVault access list and last rotation date
- Annual review record of this policy and the custodian list

## 8. Known gaps (as of 2026-09-27)

- No .NET connection string in the repositories sets `SSL Mode`. Production
  strings are injected at deploy time, so verify what prod actually uses.
- KeyVault database connections explicitly use `sslmode=disable`
  (`Processity.KeyVault/.docker/*/docker-compose.yml`,
  `EnvironmentSetup/*/docker-compose.yml`).
- Production host hardening is documented in `cicd/prod-server.md` but it does
  not mention disk encryption.
- Committed development and local settings contain default passwords
  (`postgres`, `planning`); confirm none of these are used outside local
  development.

## 9. Review

Reviewed at least annually and after any change to the threat model, hosting
provider or regulatory requirement.
